## Что понял:
1. `localStorage` сохраняет данные на диске браузера, но понимает только строки. Поэтому объекты и массивы всегда нужно пропускать через `JSON.stringify()`, а при чтении через `JSON.parse()`.

2. Если в `localStorage` ещё ничего нет, метод `getItem()` вернёт `null`. Чтобы код не падал с ошибкой, нужно ставить дефолтное значение: `JSON.parse(localStorage.getItem('books')) || []`.

3. Чтобы интерфейс не рассинхронизировался, данные меняем только в массиве JavaScript, а потом сохраняем массив в `localStorage` и вызываем функцию перерисовки экрана.

4. Каждой книге обязательно нужен уникальный идентификатор (`id = Date.now()`), чтобы при удалении или смене статуса не задеть одноимённые книги.

5. Делегирование событий (Event Delegation):
Вместо того чтобы создавать десятки слушателей кликов на каждую кнопку удаления или звездочку, мы вешаем один слушатель на общий контейнер booksList. Это сильно экономит память браузера и работает для любых новых книг, которые добавятся позже.

6. UI как функция от данных:
не меняем вручную разметку в пяти местах. Наш массив books — единственный источник правды. Мы просто меняем поле в объекте (book.status = ... или book.rating = ...) и вызываем renderBooks(), который сам перерисовывает полку.

## Исследование XSS-уязвимости и безопасность:
### Что такое XSS (Cross-Site Scripting):
Это уязвимость, возникающая при прямой вставке непроверенных пользовательских данных в HTML через `innerHTML`. Если пользователь введет теги вроде `<script>` или `<img src=x onerror=...>`, браузер выполнит этот код в контексте текущей страницы, что позволяет украсть данные (например, из `localStorage` или cookie).

### https://thecode.media/chto-takoe-xss-uyazvimost/
### https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS#defenses_against_xss

### Два способа решения:
1. **Способ 1: Отказ от innerHTML в пользу чистого DOM API (`document.createElement()`)**  
   Создавать все элементы вручную в коде и наполнять их через безопасное свойство `.textContent`. Свойство `textContent` вставляет данные исключительно как текст и никогда не парсит HTML.
   * *Минус:* код создания карточек сильно раздувается (десятки строчек `createElement`, `classList.add`, `appendChild`).
2. **Способ 2: Функция экранирования HTML-сущностей (`escapeHtml`)**  
   Преобразовывать спецсимволы `<`, `>`, `&`, `"`, `'` в их безопасные HTML-коды (`&lt;`, `&gt;` и т.д.) перед вставкой в шаблонную строку.
### Почему я выбрал Способ 2:
Я выбрал функцию санитизации `escapeHtml`, которая использует браузерный механизм `textContent` для автоматического экранирования. Ее легко реализовать и это позволило сохранить читаемый и лаконичный синтаксис шаблонных строк для верстки карточки книги, при этом на 100% нейтрализовать внедрение вредоносных тегов и инлайн-скриптов.

function loadScriptPromise(src) {
  return new Promise((resolve, reject) => {

    script.src = src;

    script.onload = () => resolve(script);

    script.onerror = () => reject(new Error(`Ошибка загрузки: ${src}`));

    document.head.append(script);
  });
}

###  Некоторые виды headers

**Content-Type**: показывает формат данных, которые лежат в теле.

**Access-Control-Allow-Origin: \***: Сервер говорит браузеру: «Разрешаю сайтам с других доменов/портов читать мои ответы»

**Access-Control-Allow-Methods: GET, POST, PATCH, DELETE, OPTIONS**: Список разрешенных HTTP-методов для внешних сайтов.

**Access-Control-Allow-Headers: Content-Type, Authorization**: Разрешение клиенту отправлять кастомные заголовки.

### Важные Content-Type виды

**1. application/json**: данные в формате JSON

**2. text/html; charset=utf-8**: веб-страница с разметкой.

**3. text/plain**: обычный голый текст без всякого оформления.

**4. multipart/form-data**: формат для отправки бинарных файлов (картинки, PDF, аватарки).

## Что понял: 
1. **Потоки (Readable Streams) и буферы в Node.js:** Запрос `req` передаёт данные не сразу целиком, а чанками сырых байтов (`Buffer`). Их нужно собирать через событие `'data'` и обрабатывать по событию `'end'`, после перерабатывать их функцией `toString`.

2. **Промисы и async/await:** Оборачивание событий потока Node.js в `new Promise((resolve, reject) => ...)` позволяет писать линейный и понятный асинхронный код через `await` и избегать Callback Hell.

3. **CORS и Preflight (метод OPTIONS):** Браузер в целях безопасности отправляет предварительный запрос `OPTIONS` перед запросами (`POST`, `PATCH`, `DELETE` с `Content-Type: application/json`). Сервер обязан ответить `204 No Content` с разрешающими заголовками `Access-Control-Allow-*`.

4. **Дефолт REST API:** Чёткое разделение между параметрами пути (`/books/:id` для идентификации конкретного ресурса) и Query-параметрами (`/books?status=...` для фильтрации списка).

5. **Пессимистичный UI:** Интерфейс не должен вводить пользователя в заблуждение — все изменения на экране происходят строго после успешного ответа сервера (`response.ok`).

## С чем возникли сложности:
- **Особенность `fetch()` при ошибках HTTP:** `fetch` не падает в блок `catch` при статус-кодах 400, 404 или 500, так как считает сам факт ответа сервера успехом. Для перехвата ошибок обязательна проверка `if (!response.ok)`.
- **Парсинг некорректных URL (`new URL`):** парсер `new URL(req.url, base)` в соответствии со стандартом WHATWG выбрасывает ошибку `ERR_INVALID_URL` при относительных путях вроде `//`. Без блока `try...catch` это приводило к падению процесса Node.js вместо возврата клиенту `400 Bad Request`.
- **Пустые значения при валидации `PATCH`:** проверка вида `if (updates.status)` пропускала пустую строку `""` или `null`, обходя валидацию допустимых статусов. Для частичных обновлений обязательна строгая проверка через `updates.status !== undefined`.
- **Блочная область видимости в `try catch`:** переменные, объявленные через `const` внутри `try`, недоступны снаружи блока. Чтобы объект `parsedUrl` был доступен дальше по всей цепочке роутинга, его потребовалось объявить через `let` перед блоком `try`.

**package.json** - это паспорт проекта

  представляет собой центральный репозиторий настроек для инструментальных средств, используемых в проекте.
  **Свойства package.json**

  - **name** — задаёт имя приложения (пакета).
  - **version** — содержит сведения о текущей версии приложения.
  - **description** — краткое описание приложения.
  - **main** — задаёт точку входа в приложение.
  - **private** — если данное свойство установлено в true, это позволяет предотвратить случайную публикацию пакета в npm.
  - **scripts** — задаёт набор Node.js-скриптов, которые можно запускать.
  - **dependencies** — содержит список npm-пакетов, от которых зависит приложение.
  - **devDependencies** — содержит список npm-пакетов, используемых при разработке проекта, но не при его реальной работе.
  - **engines** — задаёт список версий Node.js, на которых работает приложение.
  - **browserlist** — используется для хранения списка браузеров (и их версий), которые должно поддерживать приложение.

### 2. Консольный клиент `psql` (CLI):
`psql` — это основной терминальный интерактивный клиент для управления базой данных, выполнения SQL-запросов и скриптов.

**Подключение к серверу:**
```bash
psql -U postgres -h localhost -p 5432
```

**Ключевые команды `psql`:**
- `\l` — список всех доступных баз данных на сервере (List databases).
- `\c <имя_базы>` — подключиться к выбранной базе данных (Connect).
- `\dt` — список всех таблиц в текущей базе данных (List tables).
- `\d <имя_таблицы>` — подробная схема таблицы (колонки, типы данных, ограничения, внешние ключи и индексы).
- `\du` — список всех пользователей и их ролей/прав (List users/roles).
- `\dn` — список схем (Schemas) в базе.
- `\?` — вывод полной справки по всем служебным метакомандам `psql`.
- `\h <КОМАНДА>` — справка по синтаксису конкретной SQL-команды (например, `\h CREATE TABLE`).
- `\q` — безопасный выход из консоли `psql` (Quit).

### 3. Пользователи и роли (Users & Roles):
В других системах есть отдельно юзеры и группы. В PostgreSQL разработчики сделали красивее: всё называется одним словом — Роль (Role).

**Пользователь** — это роль, у которой есть флаг LOGIN (право входить по паролю).
**Группа** — это роль без флага LOGIN. Она нужна, чтобы один раз настроить права и раздавать их пользователям (например, создать роль analysts, дать ей права только на чтение SELECT, и добавлять туда реальных стажёров).

**Создание пользователя (роли) и удаление:**
```
CREATE ROLE book_user WITH LOGIN PASSWORD 'secure_password';

или

CREATE USER book_user WITH PASSWORD 'secure_password';


DROP USER book_user;
Если пользователь за время своей работы создал хоть одну таблицу, то выйдет ошибка

для этого: 

Передать владение всеми его таблицами главному админу
REASSIGN OWNED BY book_user TO postgres;

Сбросить все оставшиеся права и зависимости этого пользователя
DROP OWNED BY book_user;

спокойно удаляем
DROP USER book_user;
```

**Выдача прав на базу и таблицы (GRANT):**
```
GRANT ALL PRIVILEGES ON DATABASE book_shelf TO book_user;
выдает все права над датабазой пользователю book_user

REVOKE ALL PRIVILEGES ON DATABASE book_shelf FROM book_user;
отбирает все права

GRANT ALL ON ALL TABLES IN SCHEMA public TO book_user;
```

### 5. Типы данных PostgreSQL для схемы книжной полки:
- **`SERIAL`** — автоинкрементный числовой тип. Под капотом создаёт последовательность (`SEQUENCE`) и автоматически увеличивает значение на 1 при каждом `INSERT`. Используется для первичных ключей (`id`).
- **`INTEGER` / `INT`** — обычное целое число.
- **`VARCHAR(n)`** — строка переменной длины с жёстким лимитом в `n` символов.
- **`TEXT`** — строка переменной неограниченной длины. В PostgreSQL `TEXT` и `VARCHAR` работают с одинаковой производительностью.
- **`TIMESTAMP WITH TIME ZONE` (`TIMESTAMPTZ`)** — дата и время со смещением часового пояса.
- **`BOOLEAN`** — логический тип (`true` / `false`).

---

### 6. Ограничения целостности (Constraints):
- **`PRIMARY KEY`** — первичный ключ. Гарантирует уникальность каждой строки и запрещает значения `NULL`. Автоматически создаёт индекс для быстрого поиска.
- **`NOT NULL`** — запрет на сохранение пустых неопределённых значений.
- **`CHECK`** — проверка данных на соответствие условию прямо на уровне ядра СУБД:
  ```
  CHECK (rating >= 1 AND rating <= 5)
  CHECK (status IN ('want', 'reading', 'read'))
  ```
- **`DEFAULT`** — автоматическое значение по умолчанию, если поле не передано в `INSERT`:
  ```
  created_at TIMESTAMPTZ DEFAULT NOW()
  status VARCHAR(20) DEFAULT 'want'
  ```

---

### 7. Каскадное удаление (ON DELETE CASCADE):

**Как работает `ON DELETE CASCADE`:**
1. **Без `ON DELETE CASCADE`:** при попытке удалить книгу, у которой есть хотя бы одна заметка, PostgreSQL заблокирует операцию и выбросит ошибку нарушения целостности внешнего ключа. Пришлось бы вручную сначала удалять все заметки, а потом книгу.

2. **С `ON DELETE CASCADE`:** движок PostgreSQL при удалении книги (`DELETE FROM books WHERE id = ...`) автоматически и атомарно (в рамках одной транзакции) удаляет все привязанные к ней заметки из таблицы `notes`. Это гарантирует отсутствие в базе данных заметок-сирот.

---

### 8. Внешний ключ (FOREIGN KEY):

**FOREIGN KEY** это привязка к другой таблице для обьедениения связи, например есть основная таблица books и у нее есть book_id - PRIMARY KEY, другая таблица notes и там тоже есть поле book_id но здесь уже FOREIGN KEY тоесть эти notes привязаны к своим книгам.


### 9. Индексы (Indexes):
Индексы нужны для ускорения поиска записей, без индекса(seq scan) поиск идет последовательно, соответсвенно дольше и больше грузит процессор

**С индексом (index scan)** - поиск заметно ускоряется, занимает доли милисекунды благодоря бинарному поиску

**Создание индекса:**
```
CREATE INDEX idx_notes_book_id ON notes(book_id);
```

**Индексы создают только на те поля, по которым ты постоянно ищешь или фильтруешь данные:**

- **PRIMARY KEY (id)** — создаётся автоматически самой базой данных.
- **FOREIGN KEY**  — нужно создавать самому обязательно. Потому что мы постоянно будем искать заметки конкретной книги: WHERE book_id = $1.
- **Поля для поиска и сортировки:** если бы у нас был миллион книг и мы постоянно искали книги по автору (WHERE author = 'Достоевский') или сортировали по дате (ORDER BY created_at), на них тоже создали бы индексы.

**У индекса также есть проблемы:**
1. **Замедление записи (INSERT, UPDATE, DELETE):**
Когда индекса нет, новый INSERT просто бросает строку в конец файла.
А если у тебя 5 индексов на таблице, при каждом добавлении строки базе нужно не только сохранить саму строку, но и перестроить и перебалансировать 5 деревьев индексов на диске. Вставка данных становится заметно медленнее.

2. **Место на диске:**
Файлы индексов занимают реальное место на SSD. Иногда индекс может весить больше, чем сама таблица с данными.

### 10. Транзакции (Transactions) и принцип ACID:
Это объединение нескольких SQL-команд в одну неделимую пачку: или выполняются ВСЕ команды, или не выполняется НИ ОДНА.

Пример — перевод денег: с одного счета списать 1000 тенге, на другой зачислить 1000 тенге. Если сервер вырубился между первой и второй командой — деньги исчезнут в никуда. В транзакции:
```
BEGIN; -- начали
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- применили всё сразу
```
Если где-то случилась ошибка, вызывается ROLLBACK, и база возвращается в исходное состояние до начала транзакции.


### 11. Схемы (Schemas):

**Иерархия в PostgreSQL:** База данных -> Схема -> Таблица

**Пример:**
- **База данных** — это отдельный жёсткий диск.
- **Схема** — это папка на этом диске.
- **Таблица** — это конкретный файл (Excel-таблица), лежащий внутри этой папки.

**Схема** - Пространство имён (namespace), или просто папка внутри базы данных, которая группирует таблицы, функции и типы.

**Схема по умолчанию** — **public**: Когда ты создаёшь новую базу, в ней автоматически уже есть схема с названием public.

**Зачем нужны схемы:**

**1. Разделение проекта на модули:** В больших проектах таблицы делят по схемам, чтобы не было свалки в одном месте. Например:

  - auth.users, auth.tokens (модуль авторизации)
  - billing.invoices, billing.payments (модуль платежей)
  - public.books (основной контент)

**2. Одинаковые имена таблиц:** В разных схемах могут быть таблицы с одинаковыми именами, и они не будут конфликтовать: shop_a.orders и shop_b.orders.

**3. Права доступа:** Можно дать пользователю права на чтение только одной схемы (например, аналитикам открыть только схему analytics, закрыв доступ к billing).


**Создание и удаление схемы:**
```
CREATE SCHEMA my_schema;

DROP SCHEMA my_schema CASCADE;
```

### 12. Команды SQL:
- **JOIN:**
  ```
  SELECT b.id, b.title, n.text, n.created_at
  FROM books b
  JOIN notes n ON b.id = n.book_id;
  ```
- **Агрегатные функции и GROUP BY:**
  - **COUNT(*) / COUNT(col)** — количество строк.
  - **AVG(col)** — среднее значение (например, средний рейтинг книги).
  - **SUM(col)** — сумма.
  - **MIN(col) / MAX(col)** — минимум / максимум.

  **GROUP BY:** Групирует строки. Правило: все колонки в SELECT, к которым не применена функция, обязаны быть указаны в GROUP BY.
  ```
  SELECT b.id, b.title, COUNT(n.id) AS notes_count
  FROM books b
  LEFT JOIN notes n ON b.id = n.book_id
  GROUP BY b.id, b.title;
  ```

- **WHERE и HAVING:**
  - WHERE — фильтрует строки ДО группировки (по обычным полям таблицы).
  - HAVING — фильтрует группы ПОСЛЕ агрегации (по результатам COUNT, AVG и т.д.).
  ```
  SELECT b.title, COUNT(n.id) AS notes_count
  FROM books b
  LEFT JOIN notes n ON b.id = n.book_id
  WHERE b.status = 'read'          только прочитанные книги
  GROUP BY b.id, b.title
  HAVING COUNT(n.id) > 1;          только у которых больше 1 заметки
  ```

- **COALESCE:** - Спасатель от null(значение по умолчанию)

  Функция **COALESCE** проверяет:
    - Если первое значение НЕ null — отдаёт его .
    - Если первое значение равно null — отдаёт запасной вариант .

  `const notes = book.notes ?? []` - аналог в js


- **Агрегация строк:**
 

  - **string_agg** — склеивает текст через разделитель или перенос строки:
    ```
    SELECT b.title, string_agg(n.text, '  |  ') AS all_notes
    FROM books b
    LEFT JOIN notes n ON b.id = n.book_id
    GROUP BY b.id, b.title;
    ```
  - **json_agg** - упаковывает обьекты в готовый JSON-массив:
    ```
    SELECT b.id, b.title, json_agg(json_build_object('id', n.id, 'text', n.text)) AS notes
    FROM books b
    LEFT JOIN notes n ON b.id = n.book_id
    GROUP BY b.id;
    ```

  - **json_build_object** - строит один объект {}
  ```
  json_build_object('id', n.id, 'text', n.text)

  Вывод:
  { "id": 1, "text": "Отличная книга" }
  ```


## Пакет pg(node-postgres)

**Client, Pool** - это типы подключения к базе данных

**Client** - одиночное подключение(используется для разовых скриптов)

**Pool** - групповое подключение(используется когда делают много запросов и много людей)

**подключение через Pool**
- `const { Pool } = require('pg');`

**подключение через Client**
- `const { Client } = require('pg');`

**можно использовать сразу 2**
- `const { Pool, Client } = require("pg");`


`new Client(config) / new Pool(config)` - создание клиента/пула


**Пример config:**
```
const config = {
  host: 'localhost',
  port: 5432,
  user: 'postgres',
  password: 'твой_пароль',
  database: 'postgres',
};


const client = new Client(config);
const pool = new Pool(config);
```

**Команда: `.connect()`**
Для подключения клиента, используется в основном с Client

`.release()` вернуть/отпустить клиента обратно в пул если используешь в pool обязательно

**Команда: `.query(...)` - запрос** 

`const res = await pool.query(...)`

`res.rows` - массив строк из базы данных

`res.rowCount` - количество строк которые затронул запрос

**Параметризованный запрос**
```
const text = 'INSERT INTO users(name, email) VALUES($1, $2) RETURNING *'
const values = ['brianc', 'brian.m.carlson@gmail.com']
 
const res = await client.query(text, values)
console.log(res.rows[0])
// { name: 'brianc', email: 'brian.m.carlson@gmail.com' }
```
**$1, $2... это места в которые будут вставлятся данные из 2 параметра query() по очереди с начала до конца**

`await client.end() / await pool.end()`
Закрывает соединения, чтобы скрипт Node.js не зависал в терминале.


## Что понял:
1. **Разница между `Client` и `Pool`:**
   - **`Client`** держит ровно одно физическое соединение. Он выполняет строго один запрос за раз и требует ручного подключения (`connect()`) и закрытия (`end()`). Подходит для разовых утилит и скриптов.
   - **`Pool`** — это пул (набор) переиспользуемых клиентов. Он держит открытыми несколько соединений и выдаёт свободного клиента при запросе от пользователя. Необходим для долгоживущего веб-сервера, чтобы не тратить ресурсы на повторное TCP-рукопожатие при каждом HTTP-запросе.
2. **Обычные vs Параметризованные запросы (`$1, $2`):**
   - Обычная склейка строк через `${value}` опасна уязвимостью SQL Injection и ломается на кавычках (например, в названиях вроде `Mcdonald's`).
   - Параметризованный запрос разделяет команду и данные: Node.js передаёт каркас SQL и массив значений раздельно. База данных сначала компилирует структуру команды, а значения подставляет строго как сырые данные, что гарантирует 100% безопасность.
3. **Результат `res`:**
   - Результат запроса всегда лежит массивом объектов в `res.rows`.
   - Поле `res.rowCount` содержит количество затронутых строк (позволяет легко возвращать 404, если при DELETE/UPDATE ничего не найдено).
4. **Каскадное удаление (ON DELETE CASCADE):**
   - Использование каскадного удаления на уровне внешнего ключа гарантирует реляционную целостность: удаление родительской сущности автоматически очищает все связанные дочерние записи, исключая возникновение «мусорных» данных.
5. **Изоляция баз данных:**
   - Дефолтная база `postgres` предназначена только для первоначального входа и административных задач. Для приложения обязательно создаётся отдельная база данных.

### Использование ИИ

### 1.
* **Запрос:** Как работают параметры `$1, $2` в библиотеке `pg` и почему нельзя подставлять переменные в SQL через шаблонные строки `${...}`?
* **Ответ ИИ:** Разбор механизма параметризованных запросов, защита от SQL Injection и разделение парсинга структуры SQL от передачи сырых пользовательских данных.

### 2.
* **Запрос:** Что такое индексы в PostgreSQL?
* **Ответ ИИ:** Принцип телефонного справочника, сбалансированное дерево B-Tree, ускорение выборки связанных заметок `WHERE book_id = $1` и разбор платы за индексы (замедление INSERT/UPDATE и расход места на диске).

### 3.
* **Запрос:** Как управлять правами пользователей в PostgreSQL?
* **Ответ ИИ:** Принцип наименьших привилегий, команда `REVOKE` для ограничения доступа, разбор зависимости объектов от роли и цепочка команд `REASSIGN OWNED BY ...` + `DROP OWNED BY ...` перед удалением.

### 4. 
* **Запрос:**  зачем писать ON DELETE CASCADE, если можно просто написать CASCADE, когда удаляешь?
* **Ответ ИИ:** DROP TABLE ... CASCADE — уничтожает таблицу и её структуру при инициализации/миграции. ON DELETE CASCADE — правило для обычных пользователей: удалил книгу (DELETE FROM books...) -> её заметки удалились следом автоматически.

### 5.
* **Запрос:**  Как мне SELECT сделать с теми запросами, которые по-разному будут? Вдруг он заходит по ID и по автору, либо по автору и по статусу посмотреть, поиск. Как бы сделать это? 
* **Ответ ИИ:** Чтобы не писать 20 разных if/else на каждый случай, в веб-разработке используют паттерн «Двух массивов» (conditions и values). Мы заводим два пустых массива:
**conditions = []** — сюда складываем кусочки условий для WHERE (например, author ILIKE $1, status = $2).
**values = []** — сюда складываем сами чистые значения, чтобы избежать SQL-инъекций.
А номер $1, $2, $3... вычисляется автоматически по длине массива values.length!
